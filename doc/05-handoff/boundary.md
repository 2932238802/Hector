# 设计层 / 实现层的职责边界

> 一句话：**设计层决定「游戏是什么」，实现层决定「怎么跑起来」。**
> 两层之间靠文档与数据契约连接；任何一方不得越界替对方做决定。

## 1. 设计层（本 Agent 负责）

**产出**

- `00-vision` / `01-loop` / `02-systems` / `03-content` / `04-slice` 下的设计文档。
- 规则、数值、内容条目、术语、玩家体验目标。
- 数据契约（`data-contract.md`）与验收标准。
- 未决问题登记（`OPEN-QUESTIONS.md`）。

**禁止**

- 不写 `.gd` / `.py` / `.js` / 场景文件 / 构建脚本。
- 不建 Godot 工程、不选具体实现方案（用 Resource 还是 JSON、用轮询还是信号，由实现层决定，只要满足契约）。
- 不替实现层决定目录结构、性能方案、UI 框架。
- 不在文档里写"实现时用某某 API"这类指令——只写**行为要求**。

**允许**

- 规定**外部行为**：改数据后多久生效、哪些字段即时/下场生效、工具必须能做什么。
- 规定**数据语义**：字段含义、取值范围、枚举值。

## 2. 实现层（开发 Agent 负责）

**产出**

- Godot 4 工程、场景、脚本、数据加载与热更。
- 本地服务端与网页调参工具。
- 构建、导出、测试。

**必须**

- 严格按 `data-contract.md` 读写数据；字段名、枚举值不得改名。
- 满足 `tuning-tool.md` / `hot-reload.md` 的验收标准。
- 发现文档歧义或缺字段 → 写进 `OPEN-QUESTIONS.md`，**不自行假设后硬编码**。
- 数值、规则、文案**只能从数据文件读**，不得在代码里写死第二份。

**禁止**

- 不改设计规则、不改数值、不改文案（包括"顺手优化"）。
- 不新增玩家可见的机制。
- 不以"实现方便"为由改数据格式——要改先登记问题。

**允许**

- 提出实现层建议（性能、工具交互），由设计层决定是否采纳。
- 在不改变外部行为的前提下自由选择内部结构。

## 3. 接口：谁改什么

| 对象 | 设计层 | 实现层 |
|---|---|---|
| 规则 / 数值 / 文案 | 决定 | 只读，不得改 |
| 数据文件字段 | 定义语义与取值 | 按契约读写，不改名 |
| 战斗结算公式 | 决定 | 实现 |
| 热更触发方式 | 只要求外部行为 | 自由选择 |
| 网页 UI 布局 | 不规定 | 自由决定 |
| 构建 / 导出 | 不参与 | 负责 |

## 4. 变更流程

1. 设计层改文档 → 同步登记或关闭 `OPEN-QUESTIONS` 条目。
2. 实现层按新文档改代码与数据。
3. 若实现层认为文档不可实现或自相矛盾：**先提问，再动手**；提问期间不写猜测性代码。
4. 设计层回答后，把结论写回文档，再继续。

## 5. 文档可信度标记

- `status: living`：长期有效，随设计变更更新。
- `status: draft`：可玩但未定稿，实现时按当前版本做，允许后续改。
- 标了「**旧候选 / 历史占位**」的段落**不要实现**，只是留档。
- `OPEN-QUESTIONS.md` 里 `open` 的条目：**实现时必须按默认值或占位处理，并留出可配置项**，不得写死。
